# Computer MCP 1.1 Development Roadmap

Status: **development line, no release target yet**

Branch: `dev/1.1`

Development checkpoint 1: **Process Capability Token + filtered process listing implemented and verified**. No release has been created.

Computer MCP 1.0.4 is the frozen production baseline. 1.1 focuses on product quality, control, observability, configuration, and context efficiency rather than expanding the low-level tool count.

## Product boundary

Computer MCP owns:

- ChatGPT / MCP transport compatibility;
- secure local onboarding and Tunnel integration;
- stable logical client/device identity;
- product-facing configuration and diagnostics;
- capability presentation and compatibility aliases;
- local native permission hosts;
- safe rollout/dogfood of OWL Runtime contracts.

Computer MCP must not create a second generic:

- persistent Task engine;
- scheduler;
- approval/policy engine;
- verifier kernel;
- workspace ownership protocol;
- generic provider kernel;
- long-term Runtime health truth.

Those belong to OWL Runtime. OWL Worker owns commercial Worker UX such as My Workers, Run History, Approvals, Needs Attention, templates, and billing.

## Competitive inputs

### Desktop Commander

Useful ideas to adopt selectively:

- dynamic server configuration through tools;
- paginated/streamed process output;
- search sessions rather than one huge blocking recursive search;
- recent activity / usage diagnostics;
- strong document workflows for PDF/DOCX/XLSX;
- remote multi-device product model;
- explicit local security guardrails and optional isolation.

Do not copy its architecture blindly. Computer MCP already has stronger immutable production, native macOS permission identities, durable process metadata, Runtime lifecycle, and Tunnel packaging.

### Playwright MCP

Useful ideas:

- structured accessibility observations instead of screenshot-only control;
- local `find` over an existing observation instead of repeatedly returning a full tree;
- token/context-size discipline;
- persistent browser state;
- explicit separation between observation and action.

Security lesson:

- accessibility/DOM observations can contain indirect prompt injection;
- raw provider observations must not automatically become trusted instructions.

### OWL Lab

Computer MCP 1.1 should align toward:

- RuntimeClient public contracts;
- Observation ABI;
- Verifier receipts;
- process-scoped reconnect/control authority;
- capability/provider discovery;
- Health / Needs Attention signals;
- ExecutionTarget / provider affinity.

Production remains standalone through 1.x. OWL-backed work is development/test dogfood only until the deliberate 2.0 architecture gate.

# P0 — Reliability and reconnect ownership

## 1. Process Capability Token

Problem observed in real ChatGPT dogfood:

- `start_process` succeeds;
- ChatGPT transport/session rotates;
- `kill_process` can reject the same conversation with `PROCESS_OWNED`.

Implement process-scoped reconnect authority:

- generate a cryptographically random control token when a managed process starts;
- persist only a one-way token hash in encrypted process metadata;
- return the raw token once to the caller;
- accept the token on process control calls across transport rotation;
- keep logical-owner and Task ownership as compatible authorization paths;
- never expose tokens from `list_processes`, health, audit, or support bundles;
- rotate token on explicit orphan/recovered-process claim.

Acceptance:

- start under MCP transport A;
- transport A disappears;
- control under transport B with valid token succeeds;
- invalid/missing token from unrelated owner fails;
- token survives Runtime restart through hash verification;
- logs/audit contain no raw token.

## 2. Process list ergonomics

Add:

- `running_only`;
- `status`;
- `limit`;
- `since`;
- `owner_scope`.

Default output should not dump hundreds of historical exited processes.

## 3. Client identity diagnostics

Expose whether current ownership is:

- stable explicit logical owner;
- transport fallback;
- Task/process capability.

Never infer identity from IP/User-Agent/timing.

# P0 — Search and long-running work UX

## 4. Search sessions

Replace blocking all-tree search as the preferred large-search path:

```text
start_search
get_search_results
stop_search
list_active_searches
```

Properties:

- result pagination;
- bounded per-call latency;
- cancellation;
- progress counters;
- exclude patterns;
- file name / content modes;
- optional ripgrep provider;
- no giant result payloads.

Keep `search_files` as a compatibility convenience for small bounded searches.

## 5. Long-running shell UX

- encourage explicit `workspace_mode=read` for observation commands;
- surface current resource/lease reason on contention;
- make timeout responses state whether work is still running or was cancelled;
- add concise process progress/status summaries;
- preserve fast-fail under contention.

Do not heuristically mark arbitrary shell commands read-only.

# P0 — Conversation Configuration Domain

The user should be able to say:

- “把 wake name 改成 Friday”
- “只允许访问 Work 和 Downloads”
- “禁止删除文件”
- “允许 Git push”
- “看看现在有哪些权限”

Introduce a product configuration surface:

```text
config.get
config.list
config.plan
config.apply
config.reset
config.add_allowed_directory
config.remove_allowed_directory
config.set_capability
config.set_wake_name
config.set_aliases
```

Rules:

- schema-validated;
- versioned;
- atomic writes;
- backup before mutation;
- health check after apply;
- rollback on failed apply;
- no raw secret values returned;
- high-impact changes require explicit confirmation.

Risk examples:

- low: wake name, aliases;
- medium: browser/gui/shell enablement, allowed folders;
- high: delete, git push, full-home scope, security-policy changes.

macOS TCC permissions remain human-controlled. Config tools may inspect status and open System Settings but may not grant Full Disk Access, Accessibility, or Screen Recording.

Tunnel API-key replacement must use a local hidden-input flow rather than asking the user to paste the secret into chat.

Future Settings UI and conversational configuration must use this same configuration backend.

# P1 — Unified Status / Doctor / Needs Attention

Add a concise product-level diagnostic model:

```text
Server        healthy
Tunnel        ready
Helper        ready
Full Disk     granted
Accessibility granted
Screen        granted
Disk space    warning
Processes     2 running
Tasks         1 needs attention
```

Provide:

- `system_status`;
- `system_doctor`;
- privacy-safe support package;
- remediation actions;
- recent error summary.

Align status semantics with OWL Runtime Health / Needs Attention without duplicating its generic health computation.

# P1 — Capability Registry

Stop treating “63 tools” as the architecture.

Every exposed capability should have metadata:

- capability id;
- domain;
- provider;
- Primitive/Skill mapping;
- read/write/side-effect class;
- required Computer MCP gate;
- required macOS permission;
- resource scope;
- background-safe;
- headless-safe;
- cancellable;
- observation channel;
- verifier/postcondition support;
- production maturity.

Domains should include at least:

- filesystem;
- process/shell;
- git;
- browser;
- desktop/native;
- transaction;
- memory/runtime compatibility;
- configuration;
- diagnostics.

Helper is one native capability provider, not the container for every capability.

---

# P1 — Observation and context efficiency

Adopt OWL Observation vocabulary incrementally without switching the 1.x production backend.

For desktop/browser/file/process observations:

- normalize concise summaries;
- expose evidence references;
- allow targeted `find`/query operations;
- cap large snapshots by default;
- avoid repeating unchanged state;
- distinguish observation data from trusted instructions.

For browser/desktop side effects, begin dev/test rendering of OWL Verifier receipts:

- VERIFIED;
- FAILED;
- UNCERTAIN.

Never auto-replay a consequential action merely because the transport disconnected.

---

# P1 — Document Skills

Desktop Commander demonstrates strong user value from native PDF, DOCX, XLSX workflows.

Computer MCP should add these primarily as **Skills**, not continuously expand Primitive ABI:

- document.read;
- document.convert;
- spreadsheet.inspect;
- spreadsheet.edit;
- pdf.extract;
- pdf.create;
- office.search.

Prefer existing specialized artifact/document engines where available. Keep low-level provider details behind Skill/Provider boundaries.

---

# P1 — Onboarding and install UX

1.0.4 already provides the self-contained package.

Improve:

- end-of-install ChatGPT handoff;
- open ChatGPT Plugins page;
- tell user explicitly to choose **Tunnel**, not Server URL;
- copy/mask Tunnel ID safely;
- detect first successful tool scan where possible;
- one consolidated post-install readiness screen;
- preserve stable Runtime/Helper permission identities.

Do not automate away the final ChatGPT authorization step.

---

# P2 — Multi-device and remote execution

Desktop Commander Remote shows clear value in multiple paired machines.

Long term:

- stable device identity;
- machine nickname;
- capability/health per device;
- explicit target selection;
- no ambiguous side effects across devices.

Do not implement a second federation system inside Computer MCP. Coordinate with OWL Runtime ExecutionTarget / future multi-machine Runtime federation.

---

# P2 — Isolation

Explore:

- sandbox execution target;
- per-task temporary workspace;
- container/VM provider;
- risk-based routing to host vs sandbox.

This belongs primarily to OWL Runtime ExecutionTarget/provider work. Computer MCP should expose and select it, not implement a competing sandbox kernel.

---

# Explicit non-goals for 1.1

- no replacement of stable Runtime Host or Helper identity;
- no production switch to OWL Runtime backend;
- no second scheduler/task/approval engine;
- no arbitrary expansion of Primitive ABI;
- no cloud analytics upload by default;
- no silent macOS permission escalation.

## Development sequence

1. Process Capability Token + process filters.
2. Search sessions and context-bounded output.
3. Conversation Configuration Domain.
4. Unified status/doctor.
5. Capability Registry.
6. Observation/context-efficiency adapters.
7. Document Skills.
8. Installer/ChatGPT handoff improvements.
9. Selective OWL Runtime dev/test conformance.
10. Multi-device/sandbox design only after contracts are ready.

Release only after dogfood evidence; 1.1 has no release deadline.
